# EDL sidecars

**Import is on by default. Export is a manual task.**

EDL (Edit Decision List) files are a plain-text format understood by Kodi, MPlayer and several
other tools. A sidecar sits next to the media file with the same name and an `.edl` extension:

```text
Show - S01E01.mkv
Show - S01E01.edl
```

Import lets segments produced elsewhere be served through Jellyfin. Export makes this plugin's
results usable by players that read EDL.

## Format

Each line has three columns, separated by tabs or spaces: start seconds, end seconds, and an action
code.

```text
0.000	89.500	0
1245.300	1320.000	0
```

Action codes are the standard ones. `0` means cut or skip and is imported. `3` means commercial
break and becomes a Commercial segment. `1` (mute) and `2` (scene marker) are ignored. Blank lines
and lines starting with `#` are comments.

### The fourth column

Standard EDL has no way to say *what* is being skipped. Exports therefore add an optional fourth
column naming the segment type:

```text
0.000	89.500	0	Intro
1245.300	1320.000	0	Outro
1320.000	1350.000	0	Preview
```

Recognized names are `Intro`, `Outro`, `Recap`, `Preview` and `Commercial`. Parsers that do not
know about the column ignore it, so the file stays compatible.

## Import

Sidecars are parsed when Jellyfin asks for the item's segments, not during the analysis task, so a
file dropped next to the media takes effect immediately.

When a line has no type column, the type is guessed from position:

| Where | With one segment | With several |
| --- | --- | --- |
| First half of the runtime | Intro | earliest is Recap, the rest Intro |
| Second half | Outro | earliest is Outro, the rest Preview |

This matches the usual television layout of recap, intro, content, outro, preview. If the runtime is
unknown, everything is treated as an intro.

Duplicate lines are collapsed, and a file is capped at 10 000 segments.

## Export

**Export EDL Files** has no schedule and runs only when started from **Dashboard > Scheduled
Tasks**. It writes one sidecar per item that currently has segments, in the extended four-column
form, so a round trip through export and import preserves the types exactly.

Exported files carry a marker on the first line:

```text
# Generated by Jellyfin Segment Recognition
```

The marker does real work. Without it, an exported file would be read straight back in as a second
provider's results and every segment would appear twice.

It also decides what the task is allowed to touch. Files without the marker were written by
something else, which makes them user data and an input to the importer, so they are never
overwritten and never deleted, even when the plugin has nothing to say about that item any more.
The one exception is a file whose contents are byte-for-byte what this task would write, which is
recognized as its own output from before the marker existed and gets re-stamped rather than
orphaned.

An item whose segments have all disappeared has its own exported sidecar deleted, so stale files do
not accumulate.
